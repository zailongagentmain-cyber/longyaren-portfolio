1. What llms.txt Is, and the Problem It Was Invented to Solve

llms.txt is a plain-text Markdown file, conventionally served at the root of a domain as /llms.txt, that tells a language model or an autonomous agent what a site contains and where the substantive content lives. It is not a robots directive, it is not a sitemap, and it is not a schema.org document. It is a short, human-written index in a format that a language model can read cheaply and a program can parse mechanically.

The problem it was invented to solve is a parsing problem, and the proposal is unusually honest about that. The background section of the specification describes it plainly: agents now use websites constantly, a coding agent fetches a library's documentation to get an API call right, and a chat assistant with search reads pages to answer a question about a product. Web pages are built for people, so an HTML page wraps its information in navigation, ads, and JavaScript, and converting it back into clean text is difficult and imprecise. Context windows, while larger than they were, are still too small for most websites in their entirety, and every wasted token costs time and money. The conclusion the author draws is that agents are best served by concise, expert-level information gathered in a single, accessible location (llms-txt, 2026).

Read that as a statement about economics rather than about love for Markdown. A retrieval pipeline that fetches a page, strips navigation, strips boilerplate, strips cookie banners, strips ad slots, strips the script tags, and then still has to reconstruct meaning from what is left has spent most of its budget on your site's chrome. A 4 KB llms.txt that names your twelve important pages, summarises what each one answers, and links to them lets a well-behaved agent skip the whole exercise. The file is a hint about where the signal is, and hints are cheap for the publisher and expensive to ignore for the fetcher.

There is a second, more strategic reason for the file to exist that has nothing to do with token economics. A site's llms.txt is a declaration of editorial intent. It says: these are the pages I consider authoritative, these are the pages I consider current, and here is the plain-language summary of what this site is for. For a publisher, that is a statement about brand. For a company, it is a statement about product surface. For an agency, it is a statement about which claims you are prepared to have quoted back to you by a model that cannot be edited afterwards. That is a real asset, and it is a different asset from ranking.

The distinction that keeps the rest of this article straight: discovery is the question "can the agent find and identify the right page?"; citation is the question "does the model choose to attribute the answer to you?" The first is largely under your control. The second is a function of what the model already believes about you, which is why the largest studies of this file keep landing on a null result. Conflating the two is how a low-cost hygiene task became a false promise.

2. From a 2024 Proposal to a 2026 Specification

The proposal was first published on 3 September 2024, at a moment when the idea that language models would routinely read websites was still speculative, and it has since been revised. The current document is version two, and the changelog for that revision is dated August 2026 (llms-txt, 2026). The two-year gap is the single most important fact about this technology, because it separates the version most SEO commentary was written about from the version that actually exists today.

The adoption story in the specification is the headline: thousands of sites now publish an llms.txt file, documentation platforms generate one automatically, and coding agents use them reliably (llms-txt, 2026). The main specification page makes the same claim from the other direction, adding that Chrome's Lighthouse audits sites for one as part of its agentic browsing checks, and that the AI labs themselves publish llms.txt files for their own developer docs, naming OpenAI, Anthropic and Gemini specifically (llms-txt, 2026). That last detail is worth pausing on, because it is the strongest honest argument for the file: three of the most sophisticated consumer software companies in the world maintain one for their own documentation. If llms.txt were a dead format, they would not.

What the v2 revision actually changed falls into four groups, and each group tells you something about where the ecosystem went.

Discoverability became a first-class problem. Version one described a file but said little about how an agent holding one arbitrary page URL would find the corresponding Markdown version or the covering llms.txt. v2 answers with standard link relations: rel="alternate" type="text/markdown" points to a page's Markdown version, and rel="describedby" points to the llms.txt file that covers it, provided either as HTML <link> elements or as an HTTP Link: response header. The specification gives the header form as a single line — Link: /docs/page.html.md; rel="alternate"; type="text/markdown", /docs/llms.txt; rel="describedby" — and notes that the header form works for non-HTML resources and can be added in web server or CDN configuration without modifying any pages at all. For a site operator, that is a meaningful operational difference: you can adopt the whole contract from your edge configuration without a template change and without a deploy.

Practice diverged from the spec, and the spec blessed it. v1 specified one URL form for Markdown versions, with .md appended to the full page URL. Some publishing tools instead replace the extension, producing page.md rather than page.html.md. v2 allows both. The same instinct runs through the path rules: v1 permitted llms.txt files in subpaths without saying what that meant, and v2 defines it — a file covers the pages under its path, and where more than one file applies, agents should use the most specific one. The changelog makes the point explicitly, noting that this is what lets a site that only controls a path, such as a GitHub Pages project site, participate fully.

The consumption model was rewritten from mechanism to expectation. v1 said nothing about how llms.txt should be consumed and described a tool for expanding a file into an LLM context. v2 states the expectation directly: agents view or search the llms.txt to find what they need, then follow the relevant links, which should point to LLM-friendly content. The context-expansion tooling is no longer part of the proposal, and with it goes the special mechanical meaning of the "Optional" section that told those tools what to omit. Optional sections remain allowed and remain a useful convention for secondary links, but they no longer carry semantics. This matters more than it sounds: it means a file can no longer be audited for correctness by asking whether a parser will expand it correctly. You have to reason about whether an agent reading it as prose will do the right thing.

The framing changed from prediction to description. The background and examples now describe how agents actually use websites, rather than predicting that they might. That is a small editorial change with a large epistemic consequence: the file is no longer a speculative bet on a future web, it is a description of a present one. Which is also why the measurement question became unavoidable. Once a format describes current practice, people start asking whether it works, and the honest answer has to be in terms of what you can observe rather than what the spec intends.

One structural point about the file's position in the stack is worth making explicitly, because it is the reason many teams got the priority backwards. The specification says that llms.txt is designed to coexist with current web standards, that while sitemaps list all pages for search engines, llms.txt offers a curated overview for LLMs, and that it can complement robots.txt by providing context for allowed content (llms-txt, 2026). Curated is the operative word. A sitemap is a completeness contract. An llms.txt is an editorial contract. They are not the same artefact and they are not interchangeable, and treating them as two versions of the same thing is the most common design error I see in llms.txt implementations.

3. The Anatomy of a Valid llms.txt

The specification is unusually precise about format, because a format that is going to be parsed by programs has to be. Here is the structure as written, followed by what each part is actually for when a human writes it.

  • An optional byte-order mark (BOM). Present, tolerated, and irrelevant to almost every implementation.
  • An H1 with the name of the project or site. This is the only required section. Everything else is optional, which is precisely why so many shipped files are unusable — a title with no body satisfies the spec and tells an agent nothing.
  • A blockquote with a short summary of the project, containing key information necessary for understanding the rest of the file. This is the highest-leverage single element and the most commonly omitted. It is the part that gets quoted, summarised, or read in isolation when an agent decides whether the file is worth following.
  • Zero or more markdown sections of any type except headings, containing more detailed information about the project and how to interpret the provided files. This is where your editorial policy lives: what you cover, what you don't, who the audience is, how current the content is.
  • Zero or more markdown sections delimited by H2 headers, containing "file lists" of URLs where further detail is available. Each file list is a markdown list containing a required markdown hyperlink, then optionally a colon and notes about the file.

The mock example in the specification is the minimum viable shape, and it is worth reading as a template for the notes field, because most implementations get the link right and the note wrong:

# Title

> Optional description goes here

Optional details go here

## Section name

- [Link title](https://link_url): Optional link details

## Optional

- [Link title](https://link_url)

Two details in that example carry real weight. The first is the colon-plus-note convention: a link with a note is a link with a summary attached, and an agent that reads the note can decide whether fetching the target is worth the tokens. A bare list of sixty URLs is the single most common failure I see in shipped files, because it forces the agent into exactly the expensive mode the file was designed to avoid — open everything, judge from the content. The second is the "Optional" section, which the v2 changelog explicitly demoted from a mechanical instruction to a convention for secondary information: links an agent can skip when a shorter context is needed. Use it for your archive, your changelog, your long tail. Keep the primary sections tight enough that a model with a small context window can hold the whole file plus a couple of targets.

There is a size discipline here that almost nobody enforces. The stated design goal is that the file itself stays small enough to fit in context, that the detail lives behind the links, and is fetched only when needed. A two hundred-line llms.txt with a paragraph of prose per entry has inverted the design. It has become a sitemap with a summary attached, and the agent now has to read two hundred summaries before it can choose one, which is a strictly worse proposition than the original page it was supposed to help it skip.

The companion mechanism — the Markdown sibling — is what makes the file more than a link list. The proposal asks that pages with information agents might need provide a clean Markdown version at the same URL as the original page, either with .md appended (page.html.md) or with the extension replaced by page.md, with index.html.md or index.md for URLs without file names (llms-txt, 2026). A directory of Markdown versions is the thing that actually reduces parsing cost; the llms.txt is the map to it. Sites that publish the index but not the siblings have built a signpost to a parking lot.

One more structural convention deserves mention because it is the one most likely to be implemented wrongly by a developer who has not read the spec: a file at /docs/llms.txt covers everything under /docs/, and where more than one file applies, the most specific one wins. That is what lets a project site hosted on a path — a GitHub Pages repository site, a subdirectory deployment, a docs site under /developers/ — participate fully without owning the apex domain. If you deploy to a subpath, /llms.txt at the domain root is the wrong file, and putting it there is the sixth error discussed in section 7.

4. Who Is Supposed to Read It: The Crawler Roles That Matter

The most common misconception about llms.txt is that it is an AI crawler file in the way robots.txt is a crawler file. It is not. robots.txt controls what a named agent may fetch. llms.txt tells a fetching agent what is worth fetching once it is already there. The two act on different agents at different moments, and confusing them produces the contradiction that shows up in the data: a site that publishes an llms.txt and simultaneously blocks the search crawlers that would use it.

To make the roles concrete, here is what each major user agent is for, and what it means for the llms.txt decision. This is the layer that the platform comparison covers in detail; what matters here is the discovery consequence.

Two rows in that table carry most of the practical weight, and both are worth expanding because they are where the operational mistakes happen.

The first is Google-Extended. Google's own crawler documentation is unusually explicit that it does not have a separate HTTP request user agent string, that crawling is done with existing Google user agent strings, and that the robots.txt user-agent token is used in a control capacity. The documentation also states plainly that Google-Extended does not impact a site's inclusion in Google Search nor is it used as a ranking signal in Google Search, and explains that it is a standalone product token for managing whether content Google crawls may be used for training future generations of Gemini models and for grounding in Gemini Apps and Vertex AI (Google Search Central, 2026). Read that carefully: Google-Extended is a permission switch, not a fetcher, and nothing you do with it changes your Search presence. Teams that spend weeks debating whether to block Google-Extended are having the wrong conversation, because the answer is a policy decision about training, and it has zero effect on the traffic and citation surface they are actually trying to grow.

The second is the Anthropic crawler set, which is the clearest published example of a vendor deliberately separating the three roles. Anthropic's help documentation states that it uses a variety of robots to gather data from the public web for model development, to search the web, and to retrieve web content at users' direction, and it publishes the effect of disabling each one: ClaudeBot collects web content that could potentially contribute to training, and restricting it signals that the site's future materials should be excluded from Anthropic's training datasets; Claude-User supports Claude AI users and controls which sites can be accessed through user-initiated requests, with disabling it preventing retrieval in response to a user query and potentially reducing visibility for user-directed web search; and Claude-SearchBot navigates the web to improve search result quality for users, with disabling it preventing indexing for search optimisation and reducing visibility and accuracy in search results (Anthropic, 2026). That third description is the one that matters for the discovery question, and it is the reason a documentation site that blocks Claude-SearchBot while publishing llms.txt is making a self-defeating pair of decisions.

The contradiction to watch for in your own logs: an llms.txt served with a 200 on a date, and a search crawler that has never requested it. That is not a crawler bug. It is a permission bug, and it is invisible unless you check the log — which is why section 6 exists.

5. The 2026 Field Data: Who Has One, Who Blocks One

Two independent 2026 measurements make the current state of adoption legible, and they disagree in an instructive way. Both are worth reading with their denominators attached, because the headline percentages mean completely different things depending on which population was sampled.

The first is a September 2026 probe of well-known domains. The exact finding: "A 1 September 2026 probe of 95 well-known domains (84 reachable) found a median text-to-HTML ratio of just 2.4%, only 36% serving a valid llms.txt, and 17% blocking PerplexityBot at the root versus 6% blocking OAI-SearchBot" (GeoAura, 2026). Three things in that single sentence matter. First, the population: 95 well-known domains, of which 84 were reachable — so the 36% is a share of the reachable set, not of the 95. Second, the "valid" qualifier: a file that exists but does not conform is not counted, which is why the 36% figure is a lower bound on the file's mere presence. Third, and most usefully, the median text-to-HTML ratio of 2.4%. That number is the real story in the sentence, and it is the strongest possible argument for the llms.txt format: across a sample of prominent sites, the overwhelming majority of the HTML that a crawler downloads is not text content. This is the parsing cost the file was designed to avoid, measured.

The second measurement is later, larger, and drawn from a different population. An October 2026 access-layer panel reported that 52.4% of checkable sites serve a valid llms.txt — 173 of 330 — led by SaaS at about 60% against 1 of 29 publishers, and, crucially, that no major engine documents using it for answers (GeoAura, citing AEOeye, Oct 2026). The gap between 36% and 52.4% is not a contradiction. The first panel sampled well-known domains, of which more than a fifth were unreachable; the second sampled sites that were checkable, drawn from a population with a heavy SaaS tilt. Different denominators, different populations, different dates, both pointing the same way: adoption is real, it is well under universal, and it is concentrated in software and documentation over publishing.

That last detail is the most actionable finding in this section, and it deserves a second look. SaaS at roughly 60% versus 1 of 29 publishers is not a subtle gradient. The format was designed for documentation, the specification says so explicitly, and the adoption data shows the design working exactly as intended. If your site is a documentation site, an API reference, a developer product, or a machine-readable catalogue, llms.txt is close to table stakes. If your site is a news publication, a magazine, or a long-form essay site, adoption is close to zero and the format is probably not where your next hour should go.

Now the blocking data, because this is where the contradiction between shipping a file and blocking crawlers shows up in hard numbers. The same access-layer panel measured, across the 817 most-visited sites, that 29% name at least one AI crawler in robots.txt, and that the most-blocked tokens are training-side — CCBot at 14%, GPTBot at 14%, Bytespider at 13% and ClaudeBot at 12% — against OAI-SearchBot at 5.1% and Claude-SearchBot at 5.1% (GeoAura, 2026). The pattern is encouraging for the discovery question: site owners are much more willing to block training crawlers than retrieval crawlers, and the search-side tokens are named by only about one site in twenty.

A wider panel of 4,962 parsed robots.txt files in the Tranco top 10,000 found 19.2% blocking at least one training crawler but only 10.8% blocking at least one search crawler, a 1.8× split, and separately found that among 710 sites blocking GPTBot, 347 still allow OAI-SearchBot — the block-training-allow-search split is common, not automatic (GeoAura, 2026). That last number is a useful sanity check for your own policy: if you block GPTBot, you have not automatically blocked ChatGPT's search, and if you want that separation, you have to write it deliberately.

But the firewall layer breaks the good news, and this is the finding that should change what you check. Re-fetching 400 sites that allow every AI crawler in robots.txt, 3.8% still refused a search crawler at the firewall — with OAI-SearchBot at 3.0%, PerplexityBot at 3.3% and Claude-SearchBot at 2.7% — and 13% refused a training crawler (GeoAura, 2026). Counting both layers together, about 5% of independent sites block AI search crawlers, roughly 3× the 1.6% that a robots.txt-only audit reports (GeoAura, 2026). If you run a robots.txt audit and it tells you everything is open, that audit is wrong for roughly one site in twenty, and the gap is a WAF rule, a bot-management setting, or a CDN challenge that nobody looked at.

Two more access-layer findings bear directly on the llms.txt question. Bot protection blocked or challenged a declared crawler on 16% of 375 homepages, and 27.3% of e-commerce sites specifically — so even a crawler that has been explicitly allowed can be stopped by infrastructure that applies a challenge to anything that looks automated. And publishers close the door far more than SaaS: at least one retrieval bot was blocked by 71.1% of 38 news sites, versus 0.5% of 193 SaaS sites (GeoAura, 2026). A publication blocking three quarters of retrieval bots and shipping an llms.txt is describing a site it does not want read by machines, and the file is not going to change that.

Finally, the traffic asymmetry explains why these findings are usually invisible. Cloudflare Radar data for the seven days to 6 October 2026 put the crawl-to-refer ratio at 3,700:1 for Perplexity, 473:1 for Anthropic, 392:1 for OpenAI, 41:1 for Microsoft and 4.9:1 for Google (GeoAura, 2026). Put differently: for every hundred people who arrive at a site from a Perplexity answer, there are 370,000 page fetches by Perplexity's crawler. The cost side of AI crawling is enormous and the return side is tiny, which is precisely the imbalance that makes an llms.txt attractive in principle — you cannot make a crawler fetch less, but you can tell it where to go. What the numbers also show is that the volume is not going away, so getting the configuration right is not optional housekeeping.

And the volume is not evenly distributed. The median small-business site sees 33.7 OpenAI page fetches per ChatGPT visitor, with the middle half ranging from 12 to 101, split as 17.1 search fetches per user and 8.5 GPTBot fetches — against a pooled 153:1 on the same sites (GeoAura, 2026). And on the request-count side, training traffic dominates completely: on one monitored site over 30 days, Meta-ExternalAgent made 131,105 of 143,601 AI requests, or 91.3%, against 5.2% from OpenAI and 0.4% from PerplexityBot (GeoAura, 2026). If you are looking at your AI request volume and wondering why the numbers are so high, that is the answer: the training crawlers are the volume, and the search crawlers are the revenue path. Your robots.txt policy is where you separate them.

6. Declaration Is Not Consumption: Proving a Fetch

Everything in section 5 is about what the web looks like from the outside. What actually matters for your site is the inside: did anything fetch the file you published? Without that answer you are running a faith-based optimisation programme, and the 2026 evidence gives you good reason to be sceptical about faith-based conclusions in this area.

The absence of documented consumption is not a small detail. The access-layer panel that measured llms.txt adoption across 330 sites made the same point explicitly: while no major engine documents using it for answers (GeoAura, 2026). Not "we couldn't find it" — no major engine documents it. That is a statement about public documentation, and it is a hard constraint on what you may promise a stakeholder. You may promise that your content is easier for an agent to navigate. You may not promise that ChatGPT will cite you because the file exists.

The strongest quantitative evidence runs the same way. A large-sample study of roughly 300,000 domains found zero correlation between llms.txt and AI citations, and a separate 37,894-domain study reported no measurable citation lift either — the two together being why the conclusion drawn was that machine access matters and the file itself does not (Something Inc, 2026). The same review placed the interventions into evidence tiers, listing "publish llms.txt" as a tier-two, large-sample observation with a result of no measurable lift, alongside tier-one results for serving Markdown to AI crawlers (a randomised A/B test that came back null) and adding JSON-LD schema to already-cited pages (a difference-in-differences study that came back null to slightly negative) (Something Inc, 2026). The recommended posture that follows from that evidence is precise and, I think, exactly right: publish it if you want a cheap directory of your best pages, and do not sell it as a citation intervention.

Why the null result is not the whole story. A null correlation between having a file and being cited does not mean the file has no effect. It means the file does not overcome the dominant constraint, which is whether the model believes you are a credible source for the question. That constraint is documented elsewhere in the research: when a grounded model answers a question about a brand, it cites its sources, and across a corpus of 167,551 URL-grounded citations spanning 128 brands, 13 languages and 12 home markets, AI grounded brand answers in third-party sources 85.7% of the time while the brand's own website carried only 14.3% (Żatuchin, 2026). The same dataset found that about 18% of domains account for 80% of all citations, with a power-law fit of Zipf alpha 0.86 and R² 0.983, and that Wikipedia is the most-cited domain in 11 of the 12 languages studied (Żatuchin, 2026). Your own domain's llms.txt is not the lever. Your presence on the domains that carry the citations is.

So how do you prove consumption? You read the log, and you look for the specific request. The good news is that this is a mechanical check that takes two minutes. The bad news is that it is the step almost everyone skips, which is why a large share of the web publishes an llms.txt that has never been fetched by anything at all.

Four specific signals distinguish "we published a file" from "something read our file".

  • A GET /llms.txt request from a recognisable agent user agent. The agent matters, because a human clicking the link in a browser is not consumption — that is a self-serve visit from a person who found your file in search results, and it tells you nothing about whether a crawler uses it. Look for the documented search-side tokens: OAI-SearchBot, Claude-SearchBot, PerplexityBot, and Claude-User.
  • The Accept or User-Agent combination characteristic of an agent runtime rather than a crawler. Coding agents and chat assistants typically request a specific file, follow one or two links, and stop. A burst of one request for /llms.txt followed by requests for the .md siblings is the signature of the file being used as designed. A single isolated hit is more likely to be a compliance scanner or a link checker.
  • Subsequent requests for the files listed inside it. This is the real proof. The specification's entire design is that the file is a map: agents view or search it, then follow the relevant links. If /llms.txt is fetched and nothing listed in it is ever fetched, the file was read and ignored — which is a different problem from "nobody fetched it", and it points at the content of the file rather than at its existence.
  • Absence of a 403 or challenge on the /llms.txt path specifically. This is the one that catches people. A WAF rule, a bot-management score, or a rate limit that treats llms.txt as an unknown path can block it while leaving the rest of the site open. A 200 in a local test from your own IP proves nothing about whether a datacenter-hosted crawler was challenged on arrival.

One caveat on the whole exercise. Absence of evidence in your logs is weak evidence of absence, because a fetch that never reaches your origin — a blocked request, a challenge, a cached copy served at the edge — produces no log line at all. This is exactly why the firewall findings in section 5 matter: 3.8% of sites that allow every AI crawler in robots.txt still had a search crawler refused at the firewall, and the combined-layer share of sites blocking AI search crawlers is about 5% against the 1.6% a robots.txt-only audit reports (GeoAura, 2026). If you see no llms.txt requests at all, check the edge before you conclude the file is unwanted.

It is also worth asking what a realistic volume looks like, so that you do not mistake a low number for a broken file. The median small-business site sees 33.7 OpenAI page fetches per ChatGPT visitor (GeoAura, 2026). A file that gets a handful of requests a month from a search agent is not being ignored; it is being used at the scale the traffic justifies. Conversely, a file receiving zero requests from search agents while the same site receives thousands of GPTBot requests is being systematically excluded, and the culprit is a permission rule, not the file.

7. Six Ways llms.txt Fails in Practice

Most published llms.txt files that do not work fail in ways that are entirely predictable, and every one of them is diagnosable in under five minutes. These are the six I see most often, ordered roughly by how often they appear.

Error 1: Syntax and structure errors

The specification is not optional about its structure, and a file that breaks the structure will often be skipped rather than partially parsed. The required order is: optional BOM, then the H1, then the blockquote summary, then any number of non-heading markdown sections, then any number of H2-delimited file-list sections. The most common structural mistakes are a missing H1, a summary that is not a blockquote, a file list introduced by a paragraph instead of an H2, and — most commonly of all — a file list where the links are bare URLs rather than Markdown hyperlinks. The specification requires a markdown hyperlink with a name, optionally followed by a colon and notes, so - https://example.com/page is not a valid file-list entry while - [Pricing](https://example.com/pricing): what each tier includes is.

There is also a category of error that is not a syntax error at all but produces the same outcome: a file that satisfies the spec's minimum and says nothing. An H1 and nothing else is technically valid. It is also useless, because an agent reading it has learned your site's name and no reason to follow anything. If your file's entire content is a title, you have shipped a decoration, not a discovery contract.

Error 2: Path and case errors

Where the file lives determines what it covers, and this is the error with the most confusing symptom, because the file returns 200 and the links inside it 404. The rules are simple: a file at /llms.txt covers the whole site; a file at /docs/llms.txt covers everything under /docs/; where more than one file applies, the most specific one wins. Deploying to a subpath — a GitHub Pages repository site, a /blog/ installation, a regional site under /uk/ — and then putting the file at the domain apex means the file does not cover your content, and any agent that reads it will follow links relative to a path that is not yours.

Case errors are the quiet version of the same bug. A file served at /LLMS.txt, or linked from your HTML as /Llms.txt, is a different resource to a case-sensitive server, and a link checker will pass it while an agent will not. The v2 link-relation mechanism makes this worse if you are not careful: rel="describedby" pointing at a path that differs in case from the actual file is a broken contract that still returns a valid-looking 200 on the HTML page.

Error 3: Conflicting with robots.txt

This is the error with the largest measured footprint, and it is the reason section 5 spent so long on blocking rates. An llms.txt that is served with a 200 while the crawlers that would use it are disallowed in robots.txt is a declaration to a locked door. The measured shape of this is well documented: across the 817 most-visited sites, 29% name at least one AI crawler in robots.txt, and the training-side tokens are the popular ones, with CCBot and GPTBot each named by 14% of sites and Bytespider and ClaudeBot by 13% and 12% (GeoAura, 2026). Blocking the training crawler while allowing the search crawler is a legitimate and common policy, and the data suggests most publishers who block one are not blocking the other by default.

But there is a subtler variant of this conflict that has nothing to do with the AI tokens: your llms.txt links to URLs that your own robots.txt disallows. This happens when a Disallow rule covers a path prefix that the file lists, or when a robots.txt rule was written to block a staging path and unintentionally covers a section you have just added to your llms.txt. The agent follows the link, hits the disallow, and stops — and the failure is invisible because every individual URL behaves normally when fetched by a browser.

Error 4: Linking to non-canonical URLs

The URLs inside an llms.txt should be the URLs you want to be credited for, which means the canonical ones. Three common mistakes: listing URLs with tracking parameters appended, which fragments the identity of the page and can point at a variant you do not want indexed; listing http:// versions of https:// pages; and listing URLs that redirect, including trailing-slash variants, uppercase paths, or marketing-campaign paths that no longer resolve. Every one of these makes the agent do a redirect chase, and every one of them dilutes the link equity of the specific page you meant to name.

The 2026 field data makes the underlying problem measurable rather than theoretical. In a probe of 95 well-known domains, 84 of them reachable, the median text-to-HTML ratio was just 2.4% (GeoAura, 2026). A site whose HTML is 97.6% non-text is a site where the agent is spending its budget on markup, and a canonical URL that redirects is a site where it is spending budget again. Both are avoidable, and both are the kind of thing that a link check on a single path will never surface.

Error 5: No dates, no ownership, no scope

A file that lists fifty URLs with no indication of which are current, which are canonical for which topic, or what the site is authoritative about, is a list of links. It leaves the agent to do the work the file exists to make unnecessary. The specification's own format supports the fix: the blockquote carries a short summary containing the key information necessary for understanding the rest of the file, and the non-heading sections carry more detailed information about the project and how to interpret the provided files. Both exist to be used.

Dates matter more than they look. The same reasoning that drives citation freshness in the AI surfaces — pages updated within 30 days receiving 3.2× more citations, with 65% of AI Overview citations coming from content published within the past year, and 89% from content published within three years (Auspia, 2026) — applies to the file itself and to the entries inside it. A file that was accurate eighteen months ago and has not been touched is actively misleading, because an agent will treat a stale index as a current one. At minimum, put a last-updated date in the body text, and preferably put a date against each entry.

Error 6: Treating a JavaScript-rendered page as if it were a static file

This one is specific to the Markdown-sibling mechanism and it is where the "cheap directory" idea quietly breaks. If your llms.txt points at page.html.md variants that are generated by rendering the page and dumping the result, then you have not saved the agent any parsing cost — you have made it fetch the same HTML, run the same JavaScript, and receive the same chrome. The whole premise is that the Markdown file is a clean, pre-extracted representation, and a generated-by-rendering implementation defeats the premise while looking compliant.

The related failure is publishing the llms.txt and the .md siblings at different times, or from different templates, so the two drift. The specification's link-relation mechanism exists partly to prevent that: rel="alternate" type="text/markdown" and rel="describedby" are supposed to make the relationship machine-discoverable rather than human-maintained, and can be delivered in the HTTP Link: header from server or CDN configuration without touching a single page. If your llms.txt and your Markdown siblings are maintained by hand, expect them to diverge, and expect the divergence to be invisible until a 404 appears.

One structural trap closes this section, and it is the one that trips up project sites. A file at /docs/llms.txt covers everything under /docs/, and where more than one file applies, agents should use the most specific one (llms-txt, 2026). Deploying a project site to a subpath and putting the file at the apex means the subpath content is uncovered — and the changelog is explicit that this subpath rule is precisely what lets a site that only controls a path, such as a GitHub Pages project site, participate fully (llms-txt, 2026).

8. The Division of Labour: robots.txt, sitemap.xml, JSON-LD, llms.txt

The cleanest way to avoid the priority confusion is to give each of the four files a single job and refuse to let any of them do two. Here is the division as it actually holds in 2026, with the failure mode you get when you ask a file to do a job it was not designed for.

FileJobAudienceWhat it must never be used for
robots.txt Permission — what named agents may and may not fetch Every crawler, including AI ones Discovery. It never tells a crawler what to fetch, only what it may fetch
sitemap.xml Completeness — every indexable URL, with lastmod Search engines primarily Priority or curation. A sitemap is not a ranking hint and was never a relevance signal
JSON-LD schema Semantics — what this entity is, in a machine vocabulary Engines and agents that parse structured data Visibility of the page itself. Schema describes the page; it does not fetch it
llms.txt Curation — the small set of pages that answer your site's questions Language models and autonomous agents Permission and completeness. It cannot unblock a crawler and it should not list every URL

Three consequences follow, and each of them prevents a specific recurring mistake.

Never use llms.txt to unblock anything. Some teams treat the file as a way to signal openness to AI agents, as though a crawler blocked in robots.txt might take comfort from a friendly index. It does not work that way: robots.txt is evaluated first and independently, and the file's existence does not enter into it. If you want an agent in, you change the robots rule. That rule can be as narrow as one path, which is the sane approach — allowing OAI-SearchBot and Claude-SearchBot while continuing to block GPTBot and ClaudeBot is a coherent policy, and the 2026 data suggests roughly half of the sites that block GPTBot are running some version of it, with 347 of 710 GPTBot blockers still allowing OAI-SearchBot (GeoAura, 2026).

Never use llms.txt as a sitemap. The specification is explicit that sitemaps list all pages while llms.txt offers a curated overview (llms-txt, 2026). The failure mode is easy to spot in the wild: a llms.txt with 400 entries, generated by a plugin, none of them annotated. That file is worse than no file, because an agent will read it, sample from it, and form a worse model of your site than it would have formed from the sitemap plus a handful of well-structured pages. Curation is the feature. If you are not willing to choose twelve pages out of four hundred, you are not ready to publish the file.

Never use schema as a substitute for llms.txt, or the reverse. They answer different questions and the evidence treats them differently. A 2026 review of the intervention evidence put serving Markdown to AI crawlers in tier one with a null randomised result, adding JSON-LD schema to already-cited pages in tier one with a null-to-slightly-negative difference-in-differences result, and publishing llms.txt in tier two as a large-sample observation with no measurable lift (Something Inc, 2026). The nuance in that last item is the interesting one: the null findings were on pages that were already cited, so the studies were measuring an intervention on the wrong population. Neither result rules out a small effect, and neither addresses discovery for pages that are not yet cited — which is exactly the population an llms.txt could plausibly help, and exactly the population a panel cannot easily measure. That is a genuine open question, and it is the strongest honest argument for shipping the file: the studies so far may have been looking in the wrong place.

One asymmetry worth internalising: the cost of each of these files is roughly a day of engineering, once. The cost of the wrong priority is a quarter. That asymmetry is why the recommended order is: robots.txt correctness first, because it is the file that decides whether anything happens at all; sitemap and canonical hygiene second, because they are prerequisites for every surface; structured data third, because it is well-supported and cheap; and llms.txt last, as the newest and least load-bearing of the four. The 2026 data supports this ordering emphatically: 3.8% of sites that allow every AI crawler in robots.txt still had a search crawler refused at the firewall, meaning that the permission layer still has unexploited gains on a much larger base than the discovery layer (GeoAura, 2026).

9. Google Does Not Read llms.txt — and Why That Is Not a Reason to Skip It

Google's position is documented, and it is worth quoting precisely because the shorthand version of it ("Google doesn't care about llms.txt") is used both to dismiss the file and, wrongly, to justify not bothering with the underlying problems. The AI features guidance for site owners states that there are no additional requirements to appear in AI Overviews or AI Mode, nor other special optimisations necessary, and that the best practices for SEO remain relevant. On machine-readable files it is unambiguous: "You don't need to create new machine readable files, AI text files, or markup to appear in these features. There's also no special schema.org structured data that you need to add." The same document adds that to be eligible to be shown as a supporting link in AI Overviews or AI Mode, a page must be indexed and eligible to be shown in Google Search with a snippet, fulfilling the Search technical requirements, and that there are no additional technical requirements (Google Search Central, 2025).

Read alongside the crawler documentation, the position is complete. Google-Extended does not impact a site's inclusion in Google Search nor is it used as a ranking signal in Google Search (Google Search Central, 2026). The AI features document also states that AI is built into Search and integral to how Search functions, which makes robots.txt directives for Googlebot the control for site owners to manage access to how their sites are crawled for Search (Google Search Central, 2025).

So the accurate summary is: Google reads Googlebot's crawl of your site, and the two Google AI surfaces are assembled from that. There is no separate AI index to opt into, and llms.txt is not a route into one.

None of which is a reason to skip the file, and there are three reasons why.

One, the surfaces that matter most for discovery are not Google's. The evidence on citation pools is stark. A 320-query study across four engines — ChatGPT, Perplexity, Claude and Google AI Mode — mapping where every cited source ranked in Google and Bing organic results found that Google AI Mode pulls 93% of its cited sources from Google's own top ten, Perplexity pulls 89%, Claude drops to 53%, and ChatGPT pulls only 30%, meaning 70% of ChatGPT's cited sources rank in neither Google's nor Bing's top ten (CiteLens, via Obsurfable, 2026). The same analysis notes that Claude retrieves through Brave Search rather than Google or Bing, that the 53% figure reflects partial overlap between Brave's index and Google's rather than direct Google retrieval, and that AI Mode and AI Overviews share only 13.7% of cited URLs. The engine that ignores llms.txt is the one whose citation pool overlaps most heavily with the one that also ignores it. The engines that read a different index are the ones where a discovery file might matter — and those are the majority of the AI surface by volume.

Two, the economics of a bot relationship are changing, and the file is on the right side of the trade. Cloudflare shipped a Web Search API priced at $0.25, $5.00 and $7.00 per 1,000 requests with verified-bot compliance and source attribution as provider conditions, and pay-per-crawl under HTTP 402 went to private beta on 1 July 2025 before shifting toward per-answer payment on 1 July 2026 (GeoAura, 2026). When retrieval is priced per answer rather than per crawl, the party being paid is the party with the good content, and the party with the good content wants to be findable by exactly the agent doing the paying. A machine-readable statement of what you are authoritative about is cheap insurance in a world where access has a price attached to it.

Three, the discovery cost is going up, not down. The crawl-to-refer ratios in section 5 — 3,700:1 for Perplexity, 473:1 for Anthropic, 392:1 for OpenAI, 4.9:1 for Google — describe a web where machines read vastly more than humans click. In that world, being findable by a machine is not a nice-to-have. It is the mechanism by which a citation is even possible, because the citation comes from a page the machine chose to read.

And the commercial logic closes the loop. A study of organic LLM traffic against traditional digital channels in e-commerce, using twelve months of first-party data from 973 websites with $20 billion in combined revenue, more than 50,000 transactions from ChatGPT referrals and 164 million transactions from traditional channels, found that organic LLM traffic exhibits conversion rates and revenue per session above paid social but below all other traditional channels, with product complexity moderating the effects, and positioned the channel as one that currently serves niche informational needs rather than functioning as a broad conversion channel (Kaiser & Schulze, 2026). The channel is real and growing but still early. A referral channel that is still early is exactly where discovery infrastructure pays off, because the marginal cost of being findable now is trivial and the compounding is on the other side. On the demand side, Adobe's analysis of traffic to US retail sites found that traffic from generative AI sources increased by 1,300% between 1 November and 31 December 2024 compared with the prior year, and 1,200% in February 2025 compared with July 2024, with consumers arriving from a generative AI source showing a 23% lower bounce rate, 8% higher engagement and browsing 12% more pages per visit (Adobe, 2025).

10. The Self-Test Manual: Eight Commands You Can Run Today

Everything in this article is checkable, and the checks take minutes rather than weeks. Run these eight, in order, and you will have a complete picture of the discovery layer for your domain. Replace example.com with your own domain throughout.

# 1. Does the file exist, and is it actually the file (not a soft 404)?
curl -sS -o /dev/null -w "status=%{http_code} type=%{content_type} size=%{size_download}\n" \
  https://example.com/llms.txt

# 2. Read it. Does it have an H1, a blockquote, and file lists with notes?
curl -sS https://example.com/llms.txt | head -40

# 3. Are the first links in it canonical, absolute, and resolvable?
curl -sS https://example.com/llms.txt \
  | grep -oE '\]\(https?://[^)]+\)' | tr -d '](' | tr -d ')' \
  | while read -r u; do printf "%s " "$(curl -sS -o /dev/null -w '%{http_code}' -L --max-time 15 "$u")"; echo "$u"; done

# 4. Are the search-side AI crawlers allowed at the root?
curl -sS https://example.com/robots.txt | grep -iE 'GPTBot|OAI-SearchBot|ClaudeBot|Claude-SearchBot|Claude-User|PerplexityBot|Bytespider|Google-Extended'

# 5. Has anything actually fetched the file, and who?
grep -iE 'llms\.txt' /var/log/nginx/access.log | awk '{print $12, $13}' | sort | uniq -c | sort -rn

# 6. Which agent was it? (separate search-side from training-side)
grep -iE 'llms\.txt' /var/log/nginx/access.log \
  | grep -iE 'OAI-SearchBot|Claude-SearchBot|PerplexityBot|Claude-User' | wc -l

# 7. Did the agent follow the links? (proof of consumption, not just retrieval)
grep -iE '\.md($|\?)' /var/log/nginx/access.log | awk '{print $12}' | sort | uniq -c | sort -rn | head

# 8. Is the file's own path allowed, and are the files it names allowed?
curl -sS https://example.com/robots.txt | grep -nE 'Disallow: /llms\.txt|Disallow: /docs'

Command 1 catches the most common invisible failure: a framework that serves a 200 with an HTML error page for every unknown path, or a rewrite rule that turns /llms.txt into your homepage. Check the content_type as well as the status — you want text/plain or text/markdown, and a body that starts with #.

Command 2 is where human judgement matters. Read the output as an agent would: does the blockquote say what this site is and who it is for? Are the sections organised by topic rather than by internal department? Do the entries have notes that tell an agent whether fetching the target is worth the tokens? A file that reads like an internal navigation menu fails all three tests, even if it is syntactically perfect.

Command 3 is the link check that most people skip and that catches the redirect-chasing problem described in error 4. Do not just check that it returns 200 — check with -L to follow redirects, and note the final status. A link that redirects to a canonical URL is fine; a link that redirects through a chain or lands on a homepage is not.

Command 4 is the permissions check, and the output should be read as a policy, not as a list. You are looking for one of four states: search crawlers allowed and training crawlers allowed; search allowed and training blocked (a coherent and common policy); both blocked (a deliberate decision, probably wrong if you want citations); or nothing named at all, which means the default applies and the default allows everything. Note that the 2026 panels found that a majority of sites name nothing, and that the firewall layer still blocks search crawlers on a small but real fraction of sites that allowed everything (GeoAura, 2026).

Command 5 is the one that answers the question this article exists to answer. Sort the user agent and the path together and look at the shape of the result. A handful of requests a week from a search-side agent is normal. A large number of requests from a training agent and none from a search agent means your policy is inverted. Zero requests total means either the file is not being found — which, if you have not linked it anywhere, is the most likely explanation — or something at the edge is stopping it before your origin sees it.

Commands 6 and 7 are the pair that turn a guess into a measurement. Command 6 counts fetches by agents that plausibly use the file for retrieval. Command 7 counts requests for the Markdown siblings, and it is the difference between "something fetched the index" and "something used the index". If command 6 is non-zero and command 7 is zero, your llms.txt is being read and ignored, and the fix is in the file's content — usually a missing note on each entry, or links pointing at pages with no Markdown equivalent.

Command 8 catches error 3 in its most embarrassing form: a robots.txt rule that disallows the file you are publishing, or a path prefix that covers the documents your file lists. It is worth running that check against the specific paths named in your file, not just against /llms.txt, because a Disallow: /docs rule will silently neuter a file full of /docs/ links.

Two supporting checks sit outside the log. First, confirm that the file is machine-discoverable rather than only human-discoverable: either serve the Link: header with rel="alternate" type="text/markdown" and rel="describedby", or add matching <link> elements in the HTML head, following the pattern the specification gives (llms-txt, 2026). Second, check whether the file has a date in it and whether that date is still true. Given the freshness dynamics documented for AI surfaces — pages updated within 30 days receiving 3.2× more citations, and 65% of AI Overview citations coming from content published within the past year (Auspia, 2026) — a stale index is a liability dressed as an asset, and it is the one error on this list that gets worse every month on its own.

11. The Economics: Who Should Ship It and Who Should Not

Let us put a defensible position on the budget question, because the two failure modes here are spending real money on a file that does nothing, and refusing to spend a small amount of money on a file that helps. Both are common and both are avoidable with a decision rule.

Ship it if your site is documentation, an API reference, a developer product, or a machine-readable catalogue. The adoption data is direct: SaaS at roughly 60% of checkable sites with a valid file, against 1 of 29 publishers (GeoAura, 2026). The AI labs themselves maintain one for their own developer docs (llms-txt, 2026). Coding agents are the primary consumer of the format, and a coding agent looking for an API reference is exactly the case the format was designed for. If your product has a developer audience, this is a distribution surface, and the cost of occupying it is an afternoon.

Ship it if your site has a large, well-defined set of pages that answer a small number of recurring questions — a help centre, a policy library, a product catalogue, a standards body, a university course catalogue. The economics of the format are all about compressing a large page surface into a small curated index. If you have twenty thousand URLs and twelve questions, the file is extremely valuable. If you have twelve URLs and one question, the file is theatre.

Ship it if your business sells to developers, technical buyers, or researchers, because those buyers increasingly start in an assistant and follow citations, and the citation is more likely to land on a well-structured page that a discovery file points to.

Do not ship it if you are a news or magazine publisher whose business model depends on controlling the reading experience. The data is unambiguous about how this segment behaves: at least one retrieval bot was blocked by 71.1% of 38 news sites, versus 0.5% of 193 SaaS sites (GeoAura, 2026). Publishing an llms.txt for a site whose owners block three quarters of retrieval bots is a statement about policy that contradicts the file's existence.

Do not ship it if you have fewer than about twenty pages, or if your pages are all essentially the same shape. The format's value is compression, and there is nothing to compress.

Do not ship it if you are not prepared to maintain it. This is the real disqualifier, and it is the one that gets ignored. The evidence on maintenance is unusually clear on the wider point: a page in organic position 1 is cited only 24.9% of the time across a corpus of 167,867,680 AI Overview citations, and ranked topical coverage correlates with AI citations at 0.51 against Domain Rating's 0.09 (GeoAura, 2026). In other words, in the current environment, being maintained and being topically complete predicts citation far better than being large or authoritative. An unmaintained llms.txt is a liability in exactly the same way an unmaintained cornerstone article is: it tells every agent that trusts it that your site has a curated, current answer, and then proves you do not.

The cost side, for the record. A minimal, hand-written llms.txt covering twenty pages is roughly two to three hours including the link check. A generated one that mirrors the sitemap is an afternoon of engineering and produces the wrong artefact. The Markdown siblings are the expensive part: a static-site generator with a Markdown output path does it nearly for free, and a custom stack may need a template change and a rebuild pipeline. The ongoing cost is the maintenance of one curated list plus a periodic date check, which is genuinely small, but it is not zero and it is not automatic.

One more consideration belongs here, and it is a reputational one rather than a technical one. If you ship the file and then cite it in a pitch deck as evidence that you are optimised for AI search, you have created a claim that the current evidence does not support, and you have created it in a document that outlives the conversation in which you would have to walk it back. The defensible pitch is narrower and, in my experience, more persuasive: we publish a machine-readable index of our authoritative content and we verify agent access in our own logs. That is checkable, it is true, and it signals a maturity that "we are agent-ready" does not.

12. A 90-Day Implementation Plan

The plan below is sequenced so that each phase produces an artefact you can keep even if you stop after that phase. Nothing in it depends on a claim about citation lift, because the evidence does not support one. Everything in it depends on things you can verify.

Week 1 — Establish the baseline before you change anything

Do not start by writing the file. Start by measuring, because without a baseline you cannot tell whether your changes did anything, and the entire history of this topic is a history of unmeasured changes. Run the eight commands from section 10 against your domain and save the output. Specifically capture: whether /llms.txt exists and what it returns; which AI tokens appear in your robots.txt and with what rules; the count of AI crawler requests to your root over the last 30 days, split by token; and the number of requests for any .md URLs. Also record the two headline visibility numbers your team already tracks — citations or referral sessions — so that you have something to compare against at the end of the quarter.

The output of week 1 is a one-page audit, and it is the document you will present at the end of the quarter regardless of what you do in weeks 2 to 12.

Week 2 — Fix the permission layer

This comes first because it is the layer that gates everything else, and because the 2026 measurements show it is where the unexploited gains are concentrated. Three actions: decide and write an explicit policy for each AI token you care about, separating training crawlers from search crawlers; verify at the edge that the policy is actually being applied, since 3.8% of sites that allow every AI crawler in robots.txt still had a search crawler refused at the firewall, and the combined-layer block rate is roughly three times what a robots.txt-only audit reports (GeoAura, 2026); and check that your CDN, WAF and bot-management rules do not challenge or block the paths your agent needs.

If you publish a crawler log analysis, this is the week it comes from. The mechanics of that work are covered separately in AI crawler access control and log analysis in 2026, and the per-engine reasoning about which tokens to allow is in multi-engine AI search optimisation in 2026.

Week 3 — Decide the site's authoritative set

Pick the pages that genuinely answer your site's recurring questions. This is an editorial exercise, not a technical one, and it is where the file either becomes valuable or becomes a directory listing. A good test: for each candidate, ask whether an agent that read only that page would be able to answer a real question correctly and completely. If the answer is no, it does not belong in the primary sections. Aim for between ten and thirty entries for most sites. If you find yourself at three hundred, you are mirroring a sitemap, and the format is not doing its job.

Group them by topic rather than by team. An agent does not know your org chart, and a section headed "Product Marketing" tells it nothing about which page answers which question.

Week 4 — Write the file and the machine-discoverable links

Write the file to the specification: H1, blockquote summary, a short orientation section, then H2-delimited file lists where each entry is a Markdown link with a colon-and-note. Keep the whole file small enough to read in one go. Then make it machine-discoverable using the v2 link relations — rel="alternate" type="text/markdown" and rel="describedby" — either as HTML <link> elements in the head or as an HTTP Link: response header, and the header route is worth preferring where you can, because it can be added in server or CDN configuration without modifying any page at all (llms-txt, 2026).

Also, in week 4, publish the Markdown siblings for at least the ten most important pages. The value of the file is proportional to the value of what it points at. If you can only do one thing from this whole plan, do this one: an llms.txt with no Markdown targets is a list, and a list does not save anybody a parsing step.

Weeks 5 to 6 — Validate mechanically

Run the checks from section 10 again, this time as a release gate rather than a diagnostic. Every link in the file must resolve without a redirect chain, to a canonical URL, with a 200. Every path the file names must be allowed in robots.txt and must not be challenged at the firewall. The file must contain an H1, a blockquote, at least one H2 file list, and notes on the primary entries. The file must carry a last-updated date. Put these six checks in CI if you can, because the failure mode of this artefact is rot rather than breakage.

Weeks 7 to 8 — Prove consumption, or establish that it is not happening

Now watch the logs. The question you are answering is narrow: is any search-side agent fetching /llms.txt, and is it then fetching something listed inside it? If yes, you have demonstrated discovery working and you can say so with a number behind it. If no, you have one of three problems, and they have different fixes: the file is not being found (fix the discoverability links, or link it from a page that agents already crawl), the agent is blocked (fix the permission layer from week 2), or the file is being read and ignored (fix its content — the notes are the first thing to improve).

Be disciplined about the sample size here. Monthly panel measurement of this kind is covered in AI citation volatility in 2026, and the same sampling discipline applies to log-derived counts: one quiet week proves nothing, because agent crawl behaviour is bursty and the panels that measured this report 9.2% mean URL overlap between runs of 10,000 Google AI Mode queries, with 21.2% returning zero overlap (GeoAura, 2026).

Weeks 9 to 10 — Extend the Markdown coverage

Extend the Markdown siblings to the rest of the authoritative set, and add the Link: header to the relevant page types. If you run a documentation platform, check whether it can generate the llms.txt automatically; the specification notes that documentation platforms now generate one automatically in many cases, and if yours does, the maintenance burden drops to nearly zero (llms-txt, 2026).

Weeks 11 to 12 — Wire it into the refresh cycle and report honestly

Add the file to your editorial calendar as a quarterly review, and add the "last updated" date to your content inventory. Then report: what you changed, what the log evidence shows, and — explicitly — what it did not show. The third part is the part that matters. Reporting "we shipped a machine-readable index of our authoritative content, and here is the agent traffic it received" is a complete and credible deliverable. Reporting "we shipped a machine-readable index and expect it to drive citations" is a promise you have no evidence for, and the current large-sample evidence points the other way (Something Inc, 2026).

13. The Interface with Your Content Refresh Strategy

The llms.txt is not an isolated artefact, and the way it goes wrong most often is by drifting out of sync with the content it describes. That is a content maintenance problem, and it belongs to the same discipline as the rest of your GEO programme.

The first interface is freshness, and the numbers make it non-negotiable. Pages updated within the last 30 days receive 3.2× more citations, 65% of AI Overview citations come from content published within the past year, and 89% from content published within three years (Auspia, 2026). If your llms.txt points at pages that were last touched three years ago, you have built a machine-readable index of your stalest content, and you have done it in the format specifically designed to be trusted. The refresh discipline and the llms.txt discipline are the same discipline applied to two artefacts.

The second interface is the passage-level unit. The same Auspia analysis points out that AI systems pull individual paragraphs rather than entire pages, so a page ranking 25th can still be cited if it contains the single best answer passage for a query (Auspia, 2026). This has a direct implication for how you write the notes in your file: a note that says "covers pricing tiers and refund policy" tells an agent which passage-bearing page to fetch, whereas a note that says "important" tells it nothing. The note field is a passage-level index, and it should be written at the granularity the retrieval system actually operates at.

The third interface is topical coverage, and it is the one that most changes how you run the programme. The 2026 measurement that ranked topical coverage against Domain Rating as a predictor of AI citations — 0.51 against 0.09, across a large citation corpus, with a page in organic position 1 cited only 24.9% of the time (GeoAura, 2026) — reframes what a good llms.txt looks like. It should not be a list of your best pages. It should be a map of your topical coverage, with the gaps visible, because gaps are what an agent asking about a gap will find elsewhere. The cluster and refresh methodology that produces that map is covered in AI search topic clusters and content refresh in 2026.

The fourth interface is the entity problem, and it is the one that explains the 2026 null result. When a grounded model answers a question about a brand, it cites its sources, and across 167,551 URL-grounded citations from 128 brands in 13 languages and 12 home markets, AI grounded brand answers in third-party sources 85.7% of the time while the brand's own site carried only 14.3% (Żatuchin, 2026). The same dataset found citation volume following a power law in which about 18% of domains account for 80% of all citations, and that Wikipedia is the most-cited domain in 11 of the 12 languages studied (Żatuchin, 2026). Your llms.txt is a distribution channel to your own pages; it does not move the entity signals that decide which domains get cited. Those come from third-party coverage, and the measurement discipline for tracking them is in GEO ROI and attribution in 2026.

One final framing point, because it is the one that keeps this article honest. The llms.txt is a bet on the agent side of the market, not on your content side. If your content is thin, the file is a well-organised index of nothing. If your content is strong but your entity presence is weak, the file is a well-organised index of pages the models will not attribute to you in the first place. It removes one specific friction — the cost of a machine finding and parsing your best work — and it leaves every other constraint exactly where it was. That is still worth an afternoon. It is not worth a quarter, and it is not worth a line in a strategy deck that says "and we are optimised for AI search".

Frequently asked questions

Q: Does llms.txt actually improve AI citations in 2026?

A: The available large-sample evidence says no, and you should plan accordingly. A study of roughly 300,000 domains found zero correlation between llms.txt and AI citations, and a separate 37,894-domain study reported no measurable citation lift, which is why the conclusion drawn from the two together was that machine access matters and the file itself does not (Something Inc, 2026). No major engine publicly documents using it for answers either (GeoAura, 2026). What the file can plausibly do is lower the cost of a machine finding your best pages, which is a different claim and a smaller one. If someone has told you the file lifts citations, ask them for the sample size, the control group and the measurement window — and note that the two studies above had hundreds of thousands of domains in them.

Q: How many sites actually have an llms.txt in 2026?

A: It depends entirely on the population you measure, which is why you should be suspicious of any single number. A probe of 95 well-known domains, 84 of them reachable, found 36% serving a valid llms.txt (GeoAura, 2026). A later panel of 330 checkable sites found 52.4% — 173 of 330 — with SaaS at about 60% against 1 of 29 publishers (GeoAura, citing AEOeye, Oct 2026). And the specification itself says thousands of sites publish one, with documentation platforms generating them automatically (llms-txt, 2026). The honest summary is: adoption is real, it is well short of universal, and it is heavily concentrated in software and documentation.

Q: Is llms.txt a replacement for robots.txt or for my sitemap?

A: No, and it is a different kind of artefact from both. robots.txt is a permission contract evaluated before anything is fetched. sitemap.xml is a completeness contract listing every indexable URL. llms.txt is a curation contract naming the small set of pages that answer your site's questions, and the specification describes it explicitly as a curated overview that coexists with sitemaps rather than replacing them (llms-txt, 2026). Treating the three as alternatives is the most common category error in this area, and it usually produces a file that lists 400 URLs because someone confused it with a sitemap.

Q: Does Google read llms.txt?

A: No, and Google's documentation is explicit that you do not need it. The AI features guidance states that you do not need to create new machine readable files, AI text files, or markup to appear in AI Overviews or AI Mode, and that to be eligible you need your page indexed and eligible to be shown in Search with a snippet, with no additional technical requirements (Google Search Central, 2025). Google-Extended, which is sometimes confused with an AI crawler, has no separate HTTP user agent and is a control token for training and grounding that does not affect Search inclusion or ranking (Google Search Central, 2026).

Q: If Google ignores it, why ship it at all?

A: Because Google's AI surfaces are the minority of the AI citation surface, and they are the minority precisely because they read the same index everything else already competes in. In a 320-query study across four engines, Google AI Mode drew 93% of its cited sources from Google's top ten, Perplexity 89%, Claude 53% and ChatGPT only 30% — meaning 70% of ChatGPT's cited sources rank in neither Google's nor Bing's top ten (CiteLens, via Obsurfable, 2026). The engines that read a different index are the ones where a discovery contract could plausibly matter. Add the fact that the AI labs publish llms.txt for their own developer docs, and that crawl-to-refer ratios now run to thousands of crawls per human visit, and the case is straightforward: it is cheap, it is a distribution surface, and the cost of occupying it is an afternoon.

Q: How do I know if an AI crawler actually fetched my llms.txt?

A: From your own access logs, and the check is specific: grep for llms.txt, look at the user agent, and then confirm the agent went on to request the pages listed inside the file. That second step is the one that distinguishes consumption from retrieval, and it is the step almost everyone skips. Also check that a fetch of /llms.txt is not being blocked or challenged at the edge, because a 3.8% refusal rate at the firewall was measured even among sites allowing every AI crawler in robots.txt (GeoAura, 2026). The full command set is in section 10.

Q: My llms.txt is served with a 200 but nothing has fetched it. Why?

A: Four likely reasons, in order of frequency. The file is not discoverable — nothing links to it and no rel="describedby" points at it, so a crawler has no path to it unless it guesses the path. The agent is blocked at the firewall despite an open robots.txt. The file is a soft 404 — a framework returning your homepage with a 200, so a 200 tells you nothing. Or the file is read and ignored because every entry is a bare URL with no note, so an agent has no reason to follow any of them. The first and last of those are fixed by editing the file and the discoverability links; the second is fixed in your CDN configuration.

Q: Should llms.txt list every page on my site?

A: No, and this is where most implementations go wrong. The design intent is that the file stays small enough to fit in context and the detail lives behind the links, fetched only when needed. A file with hundreds of entries and no notes is a sitemap with extra steps, and it is worse than no file because an agent will sample from it and form a poor model of your site. The specification's own convention reserves an "Optional" section for secondary links an agent can skip when a shorter context is needed (llms-txt, 2026). For most sites, ten to thirty annotated entries in the primary sections is the right size.

Q: What are the rel="alternate" and rel="describedby" link relations, and do I need them?

A: They are the v2 mechanism for making a page's Markdown version and its covering llms.txt machine-discoverable. rel="alternate" type="text/markdown" points to the Markdown version of a page and rel="describedby" points to the llms.txt that covers it, and they can be delivered as HTML <link> elements or as an HTTP Link: response header — the header route being addable in web server or CDN configuration without modifying any pages at all (llms-txt, 2026). You need them if you want agents to find your Markdown siblings without guessing URL patterns, which is the whole point of the v2 revision. If you only publish an HTML site with no Markdown siblings, they do nothing for you.

Q: How often should I update the file?

A: Whenever the pages it points at change, and at minimum once a quarter. The freshness dynamic in AI retrieval is strong: pages updated within 30 days receive 3.2× more citations, 65% of AI Overview citations come from content published within the past year and 89% from content published within three years (Auspia, 2026). A stale llms.txt is worse than none, because it is a machine-readable claim about your site's currency that the machine will trust. Put a last-updated date in the body, date the entries, and put the file in the same quarterly review as the content it describes.

Q: Does shipping an llms.txt let me block fewer AI crawlers?

A: No, and the reasoning cuts the other way. A published llms.txt is a public signal that your content is meant to be machine-read, which makes it a poor companion to a policy of blocking retrieval crawlers. The measured behaviour of publishers is stark: at least one retrieval bot was blocked by 71.1% of 38 news sites, against 0.5% of 193 SaaS sites (GeoAura, 2026). Decide your training policy on its own merits, and treat the llms.txt as a commitment to being readable by search-side agents. If you want to allow search and block training, write that split explicitly — among 710 sites blocking GPTBot, 347 still allowed OAI-SearchBot, so it is a common and coherent position (GeoAura, 2026).

Q: Is a llms.txt file enough for a coding agent to use my documentation?

A: No, and the specification is clear about why: the links in an llms.txt should point to LLM-friendly content, meaning Markdown versions of the pages, and the file is the map to that content rather than the content itself (llms-txt, 2026). This is where the format is most clearly load-bearing, because the specification notes that llms.txt files are used most heavily for software documentation, where coding agents follow them to find API references and tutorials. If your documentation has clean Markdown output, the file plus the siblings is a genuinely complete agent interface. If it does not, the file is a list of HTML pages and the agent has to do the parsing work the format exists to avoid.

Q: We are a small company with eight pages. Is this worth doing?

A: No, and there is no version of this that is worth doing for eight pages. The format's value is compression: a large page surface summarised into a small curated index. With eight pages there is nothing to compress, and the file is a maintenance liability for no benefit. The 2026 adoption data also suggests where it does pay: SaaS at roughly 60% of checkable sites with a valid file, against 1 of 29 publishers (GeoAura, 2026). If you have eight pages, spend the afternoon on the permission layer and the canonical hygiene instead, because those are the layers with the measured unexploited gains.

Q: Is there any way to make llms.txt work as a citation lever instead of just a directory?

A: Not on the current evidence, and I would be cautious about anyone claiming otherwise. The null findings were, importantly, measured on pages that were already cited, which means the studies may have been testing the intervention on the wrong population (Something Inc, 2026). The plausible hypothesis is that the file helps with discovery for pages that are not yet cited, which a panel tracking already-cited pages cannot measure. If you want to test it, the honest test is on uncited pages with a proper control, over enough repetitions to distinguish a small effect from noise — which is a research project, not a configuration change, and should be scoped as one.

Q: How does llms.txt relate to the rest of my GEO measurement stack?

A: It sits at the bottom of the funnel and it is the least likely of your instruments to show movement on its own. Your citation panel measures the outcome, your log analysis measures access, and llms.txt is a hypothesis about one step in between. The right way to evaluate it is as a change in your own funnel: did search-side agent requests for your /llms.txt go from zero to non-zero, and did requests for the pages it names go up alongside them? That is a measurable, honest, and much more defensible claim than "citations went up".
